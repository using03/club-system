# 基于Uniapp的校园社团活动管理小程序的设计与实现

---

**摘要**

随着高校社团活动日益丰富，传统的线下管理方式已难以满足信息化需求。本文设计并实现了一套基于Uniapp的校园社团活动管理小程序系统，采用前后端分离架构，前端使用Uniapp框架（Vue 2模式）开发，支持H5和微信小程序双端运行；后端使用Node.js + Express框架构建RESTful API，数据库选用MongoDB并通过Mongoose进行数据建模和操作。系统涵盖社团信息展示、社团审核管理、活动发布与报名、签到码签到验证、活动评价反馈、站内消息通知等核心功能模块，共实现20个前端页面、43个后端API接口、7个数据模型，总代码量约4764行。经测试验证，系统功能完整，运行稳定，能够有效提升校园社团活动的管理效率和参与体验。

**关键词：** Uniapp；微信小程序；社团管理；Node.js；MongoDB；签到码

---

**Abstract**

With the increasing variety of campus club activities, traditional offline management methods can no longer meet the demands of informatization. This paper designs and implements a campus club activity management mini-program system based on Uniapp, using a front-end and back-end separated architecture. The front-end is developed with the Uniapp framework (Vue 2 mode), supporting both H5 and WeChat Mini Program platforms; the back-end is built with Node.js + Express framework providing RESTful APIs, with MongoDB as the database and Mongoose for data modeling and operations. The system covers core functional modules including club information display, club approval management, activity publishing and registration, check-in code verification, activity feedback, and in-app notification center. A total of 20 front-end pages, 43 back-end API endpoints, and 7 data models are implemented, with approximately 4764 lines of code in total. Testing verifies that the system is functionally complete and operationally stable, effectively improving the management efficiency and participation experience of campus club activities.

**Keywords:** Uniapp; WeChat Mini Program; Club Management; Node.js; MongoDB; Check-in Code

## 第一章 绪论

### 1.1 选题背景与意义

高校社团是校园文化的重要载体和组成部分，是学生锻炼综合素质、拓展兴趣爱好和增强社交能力的重要平台。近年来，随着高校招生规模的持续扩大和学生课外活动需求的不断增长，社团数量和活动形式呈现出多样化的发展趋势。据统计，一所普通本科院校通常拥有数十甚至上百个学生社团，每学期组织的各类活动数量可达数百场。然而，传统的社团管理方式大多依赖纸质登记表、微信群通知、Excel表格统计等手工方式，存在诸多亟待解决的问题。

首先，信息传递效率低下。社团的活动通知主要依赖微信群消息或校园公告栏，信息覆盖面有限，容易出现遗漏。学生需要分别关注多个社团的群消息才能获取活动信息，用户体验较差。其次，报名统计工作繁琐。传统的报名方式多采用在线表单或群接龙，组织者需要手动整理报名名单、核对人数，效率低且容易出错。再次，签到管理存在漏洞。传统签到方式（如纸质签到、群打卡）容易被代签或补签，无法有效验证参与者是否真正到场。最后，活动缺乏完整的反馈闭环。活动结束后很少进行系统化的评价和反馈收集，不利于活动质量的持续改进。

与此同时，移动互联网技术和小程序生态的快速发展为解决上述问题提供了新的途径。微信小程序自2017年推出以来发展迅速，凭借"无需下载、即用即走"的特点，已经成为各类轻量级应用的首选载体。在校园场景中，学生群体对微信的使用率极高，微信小程序天然适合作为校园社团管理工具的技术载体。同时，跨平台开发框架Uniapp的日趋成熟使得"一次开发，多端部署"成为可能，开发者只需编写一套代码即可同时发布到H5和微信小程序等多个平台，大大降低了开发和维护成本。

基于以上背景，本课题旨在设计并实现一套基于Uniapp的校园社团活动管理小程序系统。系统通过数字化手段解决社团管理中的痛点问题，涵盖社团信息展示、创建审核、活动全生命周期管理、签到码验证、消息通知等核心功能，力求构建一个功能完整、操作便捷、体验良好的校园社团活动管理平台，为提升高校社团管理信息化水平提供实践参考。

### 1.2 研究现状

在社团管理信息化领域，国内外已有一定的研究和实践成果。

在国外研究方面，欧美高校普遍使用成熟的SaaS平台进行社团管理。CampusGroups是美国高校广泛使用的社团管理平台，提供了社团主页、活动日历、成员管理、费用收缴等综合功能。OrgSync（现已被Campus Labs收购）同样是一款面向高校的学生组织管理工具。这些平台功能完善、用户体验良好，但存在几个明显局限：一是针对欧美高校管理体系设计，与国内高校的管理模式和使用习惯存在差异；二是多为商业付费产品，使用成本较高；三是缺乏对微信生态的支持，无法满足国内学生的使用习惯。

在国内研究方面，随着信息化建设的推进，国内高校也开始探索社团管理的数字化解决方案。现有的社团管理系统大致可以分为三类：（1）基于传统Web技术的管理后台，如使用Java/Spring Boot或PHP开发的社团管理网站，功能较为完善但多为PC端，移动端体验不佳；（2）基于原生开发的移动应用，开发成本高且需要分别开发iOS和Android版本，维护难度大；（3）基于微信小程序的社团工具，近年来数量逐渐增多，但大多数功能较为单一，往往只实现了签到或报名等某一个功能模块，缺乏完整的业务闭环。

在技术栈方面，Node.js作为基于Chrome V8引擎的服务端JavaScript运行时，在轻量级API开发中表现出色，其事件驱动和非阻塞I/O模型使其特别适合构建高并发的Web服务。MongoDB作为文档型NoSQL数据库，其灵活的文档模型天然适合存储社团和活动的半结构化数据（如图片数组、标签列表、嵌套成员信息等）。Uniapp基于Vue.js的跨平台框架，通过条件编译机制实现一套代码多端部署，显著提升了前端开发效率。

综合来看，现有的社团管理系统在功能完整性、跨平台支持和用户体验方面仍有较大的改进空间。本课题将充分利用Uniapp的跨平台能力和Node.js + MongoDB的轻量级后端技术，设计并实现一套功能完整、覆盖社团管理核心业务闭环的小程序系统。

## 第二章 相关技术介绍

### 2.1 Uniapp技术

Uniapp是DCloud公司推出的一款基于Vue.js的跨平台应用开发框架。使用Vue.js语法编写代码，通过编译器可以将同一套代码发布到iOS、Android、H5以及各种小程序（微信、支付宝、百度、字节跳动等）等多个平台。Uniapp的核心优势在于其"一次开发，多端部署"的能力，开发者无需为每个平台单独编写代码，即可实现跨平台应用的开发和发布。

Uniapp的技术特点主要体现在以下几个方面：

（1）基于Vue.js生态。Uniapp采用Vue.js的语法规范和组件化开发模式，开发者可以充分利用Vue.js丰富的生态资源，包括各类UI组件库、状态管理工具（如Vuex/Pinia）和开发工具链。本项目采用Vue 2的Options API风格编写页面组件，代码结构清晰，易于维护。

（2）条件编译机制。Uniapp提供了条件编译功能，通过特定的注释语法可以在代码中为不同平台编写差异化的逻辑。例如，可以针对微信小程序平台使用原生的wx.login接口，而在H5平台使用自定义的登录方式。

（3）丰富的API支持。Uniapp封装了统一的API接口，涵盖网络请求（uni.request）、数据存储（uni.setStorageSync/uni.getStorageSync）、页面导航（uni.navigateTo/uni.switchTab）、文件上传（uni.uploadFile）、图片预览（uni.previewImage）等常用功能，屏蔽了不同平台的差异性。

（4）路由配置化。Uniapp通过pages.json文件统一配置页面路由、TabBar导航、全局样式等信息，页面的注册和导航管理集中且直观。

本项目前端共实现20个页面，采用Vue 2模式开发，使用HBuilderX作为主要开发工具，同时支持H5端和微信小程序端的编译和运行。

### 2.2 Node.js与Express技术

Node.js是一个基于Chrome V8引擎的JavaScript运行时环境，由Ryan Dahl于2009年创建。它采用事件驱动、非阻塞I/O模型，使得JavaScript能够在服务端运行，适合构建高性能、高并发的网络应用。Node.js的出现使得前后端可以使用同一种编程语言，降低了全栈开发的技术门槛。

Express是Node.js最流行的轻量级Web应用框架，由TJ Holowaychuk创建。Express提供了简洁灵活的路由机制、强大的中间件体系和便捷的HTTP工具方法，是构建RESTful API服务的理想选择。

本项目后端基于Express框架构建，主要使用的核心中间件包括：

（1）cors：处理跨域资源共享（CORS）请求，允许前端应用从不同域名访问后端API。

（2）express.json：解析JSON格式的请求体，使路由处理函数能够直接通过req.body获取请求参数。

（3）morgan：HTTP请求日志中间件，在开发模式下记录每个请求的方法、URL、状态码和响应时间，便于调试。

（4）express-validator：请求参数校验中间件，在路由层对用户输入进行格式和规则验证，如用户名长度限制（2-20字符）、密码最低长度（6字符）等。

（5）自定义auth中间件：JWT Token认证中间件，从请求头Authorization字段提取Token，验证有效性后将用户信息挂载到req.user对象，供后续路由处理函数使用。

后端共划分为8个路由模块、43个API接口，采用RESTful风格设计，使用统一的响应格式`{ code: 0, message: "操作成功", data: {...} }`返回数据。

### 2.3 MongoDB技术

MongoDB是由MongoDB Inc.开发的一款开源的NoSQL文档型数据库，以BSON（Binary JSON）格式存储数据。与传统的关系型数据库不同，MongoDB不需要预定义严格的表结构（Schema），每条记录以文档（Document）的形式存储，文档之间可以有不同的字段和结构。

MongoDB在本项目中的应用优势主要体现在以下几个方面：

（1）灵活的文档模型。社团和活动的数据结构包含多种类型的字段（字符串、数组、嵌套对象、日期、布尔值等），MongoDB的文档模型能够自然地表达这些半结构化数据，无需进行复杂的关系映射。

（2）嵌套文档支持。社团的成员列表直接以子文档数组的形式嵌入在社团文档中，每个成员子文档包含用户引用、角色和加入时间三个字段。这种设计避免了额外的关联表，在查询社团详情时可以一次性获取完整的成员信息。

（3）数组字段。活动的图片列表（images）、标签列表（tags）等可以直接存储为数组字段，支持原子性的数组操作（如$push、$pull等），操作简便且性能优良。

（4）索引支持。MongoDB支持多种类型的索引，本项目使用了唯一索引（如用户名唯一、报名记录的用户+活动唯一）和复合索引（如通知的用户+创建时间），确保数据一致性和查询效率。

### 2.4 Mongoose技术

Mongoose是Node.js环境下最流行的MongoDB对象文档映射（ODM，Object Document Mapping）库。它在MongoDB原生驱动的基础上提供了更高层次的抽象，主要功能包括：

（1）Schema定义。Mongoose允许开发者通过Schema定义文档的结构、字段类型和验证规则。例如，用户名字段可以定义为String类型、必填、唯一、最小长度2字符、最大长度20字符。这些约束在数据写入时自动校验，确保数据质量。

（2）模型（Model）创建。基于Schema创建的Model相当于MongoDB集合的操作接口，提供了丰富的CRUD方法，如create()、find()、findById()、findByIdAndUpdate()、findByIdAndDelete()等。

（3）中间件钩子。Mongoose支持在文档保存、删除等操作前后执行自定义逻辑。本项目在User模型的pre('save')钩子中实现了密码自动加密功能——当密码字段被修改时，自动使用bcryptjs进行哈希加密后再存入数据库。

（4）关联查询（Population）。通过populate()方法可以实现类似关系型数据库的JOIN查询，将引用字段（ObjectId）替换为关联文档的实际内容。例如，查询社团详情时通过populate将president字段的ObjectId替换为用户的昵称和头像信息。

（5）实例方法和虚拟属性。可以在Schema上定义实例方法（如comparePassword用于密码比对）和toJSON方法（自动过滤密码等敏感字段），增强数据安全性。

本项目共定义了7个Mongoose模型，对应7个MongoDB集合，涵盖了系统全部的数据存储需求。

### 2.5 JWT认证技术

JSON Web Token（JWT）是一种基于RFC 7519标准的轻量级身份认证方案，特别适用于前后端分离架构的无状态认证场景。JWT Token由三个部分组成：Header（头部，包含签名算法）、Payload（载荷，包含用户信息和过期时间）和Signature（签名，用于验证Token的完整性和真实性）。

本项目中JWT认证的工作流程如下：

（1）用户登录。用户提交用户名和密码，后端验证通过后使用jsonwebtoken库生成一个包含用户ID的JWT Token，Token有效期设置为7天，连同用户信息一起返回给客户端。

（2）Token存储。前端客户端接收到Token后，使用uni.setStorageSync将Token和用户信息存储在本地存储中。

（3）请求携带。在封装的HTTP请求工具中，每次发送请求前自动从本地存储读取Token，并将其附加到请求头的Authorization字段中（格式为Bearer <token>）。

（4）服务端验证。后端的auth中间件从请求头中提取Token，使用jsonwebtoken.verify()方法验证其有效性。验证通过后将用户ID和用户信息挂载到请求对象上，供后续路由处理函数使用。

（5）Token过期处理。当前端收到401未认证的HTTP响应时，自动清除本地存储的Token和用户信息，并跳转到登录页面引导用户重新登录。

JWT认证方案相比传统的Session认证，具有无状态、可扩展、跨域友好等优势，非常适合本项目前后端分离的架构模式。

### 2.6 Multer文件上传技术

Multer是一个用于处理multipart/form-data类型表单数据的Node.js中间件，主要用于文件上传功能的实现。在本项目中，Multer负责处理社团Logo、活动封面图和活动图片集的上传。

Multer的核心配置包括存储策略和文件过滤。存储策略使用diskStorage模式，将上传的文件保存到服务器的uploads/目录，文件名采用时间戳加随机数的方式生成以避免命名冲突。文件过滤器限制了允许上传的文件类型（仅支持jpg、png、gif、webp格式）和文件大小（单文件不超过5MB），确保上传内容的安全性和合规性。

上传完成后，后端通过Express的静态文件服务中间件（express.static）将uploads/目录对外提供HTTP访问，前端可以直接通过URL展示和预览已上传的图片。本项目提供了单图上传和多图上传两种接口，分别用于社团Logo/活动封面图和活动图片集的上传场景。

### 2.7 HBuilderX工具

HBuilderX是DCloud公司推出的一款为Uniapp量身定制的集成开发环境（IDE），是Uniapp开发的官方推荐工具。HBuilderX具有以下特点：

（1）内置Uniapp编译器。支持一键编译和运行Uniapp项目到H5、微信小程序等目标平台，无需额外配置编译环境。

（2）真机调试支持。可以通过USB连接手机进行真机调试，实时查看运行效果和调试信息。

（3）代码智能提示。针对Uniapp的API和组件提供完善的代码补全和语法提示，提升开发效率。

（4）内置终端和Git管理。集成了终端工具和Git版本控制功能，方便在IDE内完成项目管理和版本控制操作。

本项目使用HBuilderX作为前端的主要开发和调试工具，通过H5模式进行日常开发调试，通过微信小程序模式进行平台适配验证。

### 2.8 微信开发者工具

微信开发者工具是腾讯公司为微信小程序开发提供的官方IDE，是小程序开发和调试的必备工具。其主要功能包括：

（1）小程序模拟器。提供了微信客户端的运行模拟环境，可以在PC端模拟小程序的各种场景和功能，包括页面渲染、网络请求、数据存储等。

（2）调试器。提供了类似Chrome DevTools的调试面板，支持查看页面结构、样式、网络请求、控制台输出等信息。

（3）预览和上传。支持生成小程序的预览二维码供手机端扫码预览，以及将代码上传到微信公众平台进行审核和发布。

（4）真机调试。支持通过网络连接手机进行真机调试，可以在真实的微信环境中查看运行效果和调试问题。

在本项目中，通过HBuilderX将Uniapp代码编译为微信小程序格式后，使用微信开发者工具进行小程序端的调试和测试，确保应用在微信小程序平台上的兼容性和功能正确性。

### 3.2 功能性需求

#### 3.2.1 用户功能需求

通过对校园社团管理场景的调研分析，本系统涉及三类核心角色：普通学生（student）、社团管理员（club_admin）和系统管理员（admin）。各角色的功能用例描述如下。

普通学生是系统的基础用户角色，注册时默认分配。该角色可以进行以下操作：浏览首页的热门社团和最新活动、查看社团列表和社团详情、查看活动列表和活动详情、加入社团成为社团成员、报名参加活动、进行签到打卡（输入签到码）、对已签到的活动进行评价、查看消息通知、管理个人信息、申请创建社团。

社团管理员是社团审核通过后由系统自动升级的角色。该角色在普通学生功能的基础上，额外拥有以下管理功能：编辑社团信息（名称、简介、公告、Logo、标签等）、发布和编辑活动（社长和副社长均可）、管理社团成员（设置角色、移除成员、转让社长）、审核活动报名（通过/拒绝需审核的报名申请）、管理签到码（开启/刷新签到码、结束签到）。

系统管理员是后台指定的全局管理角色。该角色拥有全部普通功能及以下管理权限：审核社团创建申请（通过/拒绝并填写拒绝原因）、查看所有待审核社团列表。

在社团内部，还存在三种社团级角色：社长（president，社团最高管理者）、副社长（vice_president，可发布活动）和普通成员（member，参与社团活动）。社长是社团创建者在审核通过后自动获得的角色，社长可以将其他成员设为副社长或将副社长降为普通成员，也可以将社长职位转让给其他成员。

#### 3.2.2 用户认证功能

用户认证功能是系统的基础安全模块，主要包括以下功能需求：

（1）用户注册。用户输入用户名（2-20字符，需唯一）、密码（不少于6字符）以及可选的昵称、手机号、学号信息完成注册。注册成功后系统返回JWT Token和用户信息。

（2）用户登录。用户输入用户名和密码进行登录，系统验证凭证的正确性后返回JWT Token。密码使用bcryptjs加密比对，不以明文形式进行比较或存储。

（3）个人信息管理。已登录用户可以查看和修改个人信息，包括昵称、手机号、头像、学号等字段。

（4）认证状态维护。系统通过JWT Token维持用户的登录状态，Token有效期为7天。Token过期或无效时系统自动引导用户重新登录。

#### 3.2.3 社团管理功能

社团管理功能涵盖社团的完整生命周期，主要包括以下功能需求：

（1）社团创建与审核。学生可以提交社团创建申请，填写社团名称（需唯一）、简介、分类（学术科技、文化艺术、体育运动、志愿公益、创新创业、其他六种分类）、Logo、标签等信息。创建的社团初始状态为pending（待审核），系统自动向所有系统管理员发送审核通知。管理员审核通过后社团状态变为active，创建者角色自动升级为club_admin；管理员拒绝时必须填写拒绝原因，拒绝原因通过通知发送给申请人。

（2）被拒绝社团的处理。被拒绝的社团在"我的社团"页面显示"已拒绝"标记，用户可以查看拒绝原因。用户可以选择"修改并重新提交"（进入专用的重新申请页面修改信息后重新提交审核）或"取消申请"（彻底删除该社团记录并通知管理员）。

（3）社团信息编辑。社长可以编辑社团的名称、简介、分类、Logo、公告、标签等信息。

（4）社团信息展示。社团详情页展示完整信息：Logo（有Logo显示图片，无Logo显示文字头像）、基本信息（名称、分类、成员数、成立时间）、公告、简介和标签、成员列表（按角色用不同颜色区分）、活动历史记录。

（5）成员管理。社长可以进行以下成员管理操作：将普通成员设为副社长、将副社长降为普通成员、移除社团成员（移除时需确认）、将社长职位转让给其他成员（转让后自己变为普通成员）。

#### 3.2.4 活动管理功能

活动管理功能支持活动的全生命周期管理，主要包括以下功能需求：

（1）活动发布。社长和副社长可以发布活动，填写标题、描述、时间（开始时间和结束时间）、地点、名额上限、是否需要报名审核、封面图、标签等信息。新创建的活动默认状态为draft（草稿），可以手动切换为published（已发布）状态。

（2）活动状态自动切换。系统支持六种活动状态：draft（草稿）、published（已发布）、registration（报名中）、ongoing（进行中）、ended（已结束）、cancelled（已取消）。每次查询活动时，系统自动比较当前时间与活动的开始时间和结束时间，将过期的活动状态自动更新为ongoing或ended，无需额外的定时任务。

（3）活动报名。用户可以报名参加活动。系统支持两种报名模式：自动通过模式（报名即通过）和需审核模式（需要活动组织者审核通过后才算报名成功）。系统通过唯一索引防止同一用户重复报名同一活动，同时支持名额限制功能。

（4）活动编辑与删除。活动组织者可以修改活动信息、切换活动状态、删除活动（删除时同步清除关联的报名记录）。

（5）活动图片管理。活动支持封面图和图片集（最多9张）的上传、展示和删除。图片通过服务器端上传存储，在活动详情页以画廊形式展示。

#### 3.2.5 签到打卡功能

签到打卡功能是本系统的特色功能模块，通过签到码验证机制确保参与者到场，主要包括以下功能需求：

（1）签到码生成。活动组织者在签到记录管理页面可以开启签到码功能，系统生成随机6位数字码并以大号字体显示。组织者可以随时刷新签到码（旧码立即失效），但签到码一旦启用不可关闭回无码模式，只能选择"结束签到"。

（2）签到码验证。参与者点击"签到打卡"时，若活动未开启签到码则直接签到成功；若已开启签到码，则弹出输入框要求输入6位签到码，验证通过后签到成功。

（3）后端签到校验。签到接口依次检查以下条件：活动状态必须为进行中、当前时间必须在活动的开始时间和结束时间范围内（startTime ≤ now ≤ endTime）、用户必须已报名且报名状态为approved、不允许重复签到、签到码必须正确（如已开启）。

（4）结束签到。组织者点击"结束签到"后，活动状态标记为ended，结束时间同步更新为当前时间，未签到的参与者将无法再进行签到。

#### 3.2.6 消息通知功能

消息通知功能实现了站内通知中心，确保各角色及时获取关键业务信息，主要包括以下功能需求：

（1）通知自动触发。系统在以下11种业务场景中自动创建通知：创建社团申请时通知所有管理员、重新提交社团审核时通知所有管理员、社团审核通过时通知申请人、社团审核拒绝时通知申请人（含拒绝原因）、撤回社团申请时通知所有管理员、需审核的活动报名时通知活动组织者、报名审核通过时通知报名人、报名审核拒绝时通知报名人、新成员加入社团时通知社长、成员退出社团时通知社长、成员角色变更或被移除时通知相关人员。

（2）通知展示与交互。消息中心页面展示所有通知列表，未读消息以蓝色背景和红点标记区分。点击通知时自动标记为已读并根据通知类型跳转到相关页面（社团详情、活动详情、社团审核页等）。

（3）通知管理。支持查看未读消息数量（在"我的"页面以红色徽章形式展示）、单条标记已读、全部标记已读等操作。

### 3.3 非功能性需求

#### 3.3.1 系统易用性需求

系统的易用性需求主要包括以下几个方面：

（1）界面简洁直观。系统界面采用清晰的视觉层次和统一的设计风格，使用绿色（#4CAF50）为主色调，配合Material Design风格的卡片、按钮和图标元素，确保视觉一致性和美观度。

（2）导航清晰。采用TabBar底部导航（首页、活动、我的三个入口）和页面跳转相结合的导航方式，用户可以快速到达目标页面。各页面的标题栏明确标注当前位置，支持返回操作。

（3）操作反馈及时。所有关键操作（报名、签到、审核、修改等）完成后均通过Toast提示告知用户操作结果。危险操作（删除、移除、转让等）需要二次确认，防止误操作。

（4）跨平台一致性。系统同时支持H5和微信小程序两个平台，确保两个平台的功能和交互体验保持一致。

#### 3.3.2 系统性能需求

系统的性能需求主要包括以下几个方面：

（1）响应速度。系统API接口的平均响应时间应控制在500毫秒以内，确保用户操作的流畅性。页面加载时间不超过2秒。

（2）并发处理能力。系统应能够支持至少100名用户的同时在线访问和操作，满足一般高校社团管理的使用需求。

（3）数据查询效率。通过合理的数据库索引设计（如唯一索引、复合索引）和分页查询机制，确保在数据量增长时仍能保持良好的查询性能。

#### 3.3.3 系统安全性需求

系统的安全性需求主要包括以下几个方面：

（1）身份认证安全。用户密码使用bcryptjs进行哈希加密后存储，不以明文形式保存。密码字段在API响应中自动过滤（通过Mongoose的toJSON方法），防止泄露。采用JWT Token机制进行身份认证，Token设置合理的有效期。

（2）权限控制。系统实现了两层权限体系（系统级角色和社团级角色），各API接口根据业务需求进行权限校验。管理操作（如社团审核、成员管理、活动发布等）均验证操作者的身份和权限。

（3）输入校验。所有用户输入通过express-validator在服务端进行格式和规则校验，防止非法数据进入系统。文件上传限制了文件类型和大小，防止恶意文件上传。

（4）数据完整性。关键业务操作通过数据库唯一索引确保数据一致性，如用户名唯一、同一用户不可重复报名/签到/评价同一活动。

## 第四章 系统设计

### 4.1 模块设计

#### 4.1.1 系统模块划分

根据需求分析的结果，本系统按照功能职责划分为以下核心模块：

（1）用户认证模块。负责用户注册、登录、个人信息管理和JWT Token的生成与验证。

（2）社团管理模块。负责社团的创建、编辑、信息展示、列表查询和分类筛选。

（3）社团审核模块。负责社团创建申请的审核（通过/拒绝）、重新提交和撤回流程。

（4）成员管理模块。负责社团成员的加入、退出、角色管理、社长转让和成员移除。

（5）活动管理模块。负责活动的发布、编辑、删除、状态管理和图片管理。

（6）活动报名模块。负责活动报名、报名审核和报名记录管理。

（7）签到打卡模块。负责签到码的生成和验证、签到记录管理和签到状态查询。

（8）活动评价模块。负责活动评价的提交和查看、平均评分的计算。

（9）消息通知模块。负责通知的自动创建、展示、已读标记和跳转。

（10）文件上传模块。负责图片文件的上传、存储和访问。

#### 4.1.2 模块功能简述

各模块的核心功能简述如下：

用户认证模块提供8个API接口，包括注册、登录、获取个人信息、修改个人信息、获取我的社团、获取我的活动、获取报名记录和获取签到记录，路由前缀为/api/auth。

社团管理模块提供9个API接口，包括获取社团列表、获取社团详情、创建社团、编辑社团、获取社团活动历史、获取待审核社团列表、审核通过、审核拒绝和撤回申请，路由前缀为/api/clubs。

成员管理模块提供6个API接口，包括加入社团、退出社团、获取成员列表、修改成员角色、移除成员和社长转让，路由前缀为/api/members。

活动管理模块提供9个API接口，包括获取活动列表、获取活动详情、创建活动、编辑活动、删除活动、活动报名、审核报名、生成签到码和结束签到，路由前缀为/api/activities。

签到打卡模块提供3个API接口，包括签到、获取签到列表和查询签到状态，路由前缀为/api/checkin。

活动评价模块提供2个API接口，包括提交评价和获取评价列表，路由前缀为/api/feedback。

文件上传模块提供2个API接口，包括单图上传和多图上传，路由前缀为/api/upload。

消息通知模块提供4个API接口，包括获取通知列表、获取未读数量、标记单条已读和全部标记已读，路由前缀为/api/notifications。

#### 4.1.3 系统功能结构图

系统整体功能结构采用前后端分离的三层架构，自上而下分为表现层、业务逻辑层和数据持久层：

表现层（Uniapp前端）包含20个页面，通过pages.json配置路由和TabBar导航。TabBar页面包括首页（热门社团+最新活动）、活动列表和我的中心。非TabBar页面包括登录注册、社团相关页面（列表、详情、创建、编辑、重新申请）、活动相关页面（详情、创建、编辑）、个人中心子页面（我的社团、我的活动、报名记录、签到记录、消息中心）以及管理页面（报名审核、签到记录管理、社团审核）。前端通过封装的API模块与后端通信，使用uni.request发送HTTP请求，通过JWT Token进行身份认证。

业务逻辑层（Express后端）包含8个路由模块、43个API接口，以及JWT认证中间件、文件上传中间件、通知工具函数和活动状态自动更新工具函数等核心组件。

数据持久层（MongoDB数据库）包含7个集合（users、clubs、activities、registrations、checkins、feedbacks、notifications），通过Mongoose ODM进行数据建模和操作。

### 4.3 数据库设计

#### 4.3.1 基本实体集设计

本系统共设计7个基本实体集，各实体的属性设计如下：

**（1）用户实体（User）**

用户实体用于存储系统用户的账号信息和角色标识。核心属性包括：username（用户名，字符串类型，必填，唯一，2-20字符）、password（密码，字符串类型，必填，最少6字符，bcrypt加密存储）、nickname（昵称，字符串类型）、avatar（头像URL，字符串类型）、phone（手机号，字符串类型）、studentId（学号，字符串类型）、role（系统角色，枚举类型，取值为student/club_admin/admin，默认student）、openid（微信openid，字符串类型，预留字段）。系统通过Mongoose的pre('save')中间件钩子实现密码自动加密，通过toJSON方法自动过滤密码字段防止泄露。

**（2）社团实体（Club）**

社团实体用于存储社团的基本信息、成员列表和审核状态。核心属性包括：name（社团名称，字符串类型，必填，唯一）、description（社团简介，字符串类型）、logo（Logo图片URL，字符串类型）、foundedAt（成立时间，日期类型）、category（社团分类，枚举类型，取值为学术科技/文化艺术/体育运动/志愿公益/创新创业/其他）、president（社长，ObjectId类型，关联User）、members（成员数组，嵌套文档数组，每个元素包含user/role/joinedAt三个字段）、memberCount（成员数量，数值类型）、status（社团状态，枚举类型，取值为active/inactive/pending）、announcement（社团公告，字符串类型）、tags（标签数组，字符串数组）、rejectReason（拒绝原因，字符串类型）。

**（3）活动实体（Activity）**

活动实体用于存储活动的详细信息和签到码配置。核心属性包括：title（活动标题，字符串类型，必填）、description（活动描述，字符串类型）、club（所属社团，ObjectId类型，关联Club，必填）、organizer（组织者，ObjectId类型，关联User，必填）、startTime（开始时间，日期类型，必填）、endTime（结束时间，日期类型，必填）、location（活动地点，字符串类型，必填）、maxParticipants（最大参与人数，数值类型，0表示不限）、currentParticipants（当前参与人数，数值类型）、images（图片数组，字符串数组）、coverImage（封面图URL，字符串类型）、status（活动状态，枚举类型，取值为draft/published/registration/ongoing/ended/cancelled）、needApproval（是否需要报名审核，布尔类型）、tags（标签数组，字符串数组）、checkinCode（签到码，字符串类型）、checkinCodeEnabled（是否已启用签到码，布尔类型）。

**（4）报名实体（Registration）**

报名实体用于记录用户的活动报名信息。核心属性包括：user（报名用户，ObjectId类型，关联User，必填）、activity（报名活动，ObjectId类型，关联Activity，必填）、status（报名状态，枚举类型，取值为pending/approved/rejected/cancelled）、remark（备注，字符串类型）。通过{user, activity}联合唯一索引确保同一用户不能重复报名同一活动。

**（5）签到实体（CheckIn）**

签到实体用于记录用户的签到信息。核心属性包括：user（签到用户，ObjectId类型，关联User，必填）、activity（签到活动，ObjectId类型，关联Activity，必填）、checkInTime（签到时间，日期类型，默认当前时间）、location（签到位置，嵌套对象，包含latitude和longitude两个数值字段）。通过{user, activity}联合唯一索引防止重复签到。

**（6）评价实体（Feedback）**

评价实体用于记录用户对活动的评价信息。核心属性包括：user（评价用户，ObjectId类型，关联User，必填）、activity（评价活动，ObjectId类型，关联Activity，必填）、rating（评分，数值类型，必填，范围1-5）、comment（评价内容，字符串类型）。通过{user, activity}联合唯一索引防止重复评价。

**（7）通知实体（Notification）**

通知实体用于记录系统内的站内通知。核心属性包括：user（通知接收者，ObjectId类型，关联User，必填）、type（通知类型，枚举类型，取值为club_pending/club_approved/club_rejected/club_withdrawn/registration_pending/registration_approved/registration_rejected/member_joined/member_left/activity_reminder，必填）、title（通知标题，字符串类型，必填）、content（通知内容，字符串类型）、relatedId（关联资源ID，字符串类型）、read（是否已读，布尔类型，默认false）。通过{user, createdAt}复合索引优化用户通知列表的查询性能。

（1）代码组织规范。前端采用Uniapp标准的目录结构，按功能模块组织页面和组件。后端采用MVC模式，将路由（routes）、数据模型（models）、中间件（middleware）和工具函数（utils）分离到不同目录。

### 5.3 系统代码实现

#### 5.3.1 首页

首页是用户进入系统后看到的第一个页面，采用绿色渐变背景的标题区域搭配白色内容卡片的布局方案。页面分为两个主要区域："热门社团"横向滚动卡片区和"最新活动"纵向列表区。

在数据加载方面，首页使用Uniapp的onShow生命周期钩子在每次页面显示时触发数据加载。通过Promise.all并行请求社团列表和活动列表两个API接口，减少页面加载等待时间。社团列表限制返回6条数据，以横向滚动视图（scroll-view）的卡片形式展示，每个卡片包含Logo（有Logo显示图片、无Logo显示名称首字母的圆形文字头像）、社团名称、分类和成员数。活动列表限制返回5条已发布状态的活动，以纵向卡片列表形式展示，每个卡片包含活动标题、地点、时间和状态标签。

首页的核心代码逻辑如下：在loadData方法中，使用async/await语法配合Promise.all同时调用clubApi.getList和activityApi.getList两个接口获取数据，分别将返回的社团数组和活动数组赋值给组件的clubs和activities响应式数据。在模板层面，使用v-for指令循环渲染社团卡片和活动卡片，通过@click事件绑定实现点击跳转到社团详情页或活动详情页。

#### 5.3.2 社团详情页

社团详情页是展示社团完整信息和提供管理操作入口的核心页面。页面顶部使用绿色渐变背景展示社团Logo（或文字头像）、名称、分类、成员数和成立时间。页面主体分为四个白色卡片区域：公告区（仅在有公告时显示，橙色背景突出显示）、简介与标签区、成员列表区和活动历史区。

在成员管理方面，成员列表按角色使用不同的颜色标识——社长用橙色（#FF9800）、副社长用蓝色（#2196F3）、普通成员用绿色（#4CAF50）。当登录用户是社长时，点击其他成员卡片可以展开操作面板，显示"设为副社长"/"取消副社长"和"移除成员"按钮。成员管理操作均通过uni.showModal弹窗进行二次确认，确认后调用相应的成员管理API。

在社长转让方面，社长点击页面底部的"转让社长"按钮后弹出模态框，列出所有可转让的成员（排除社长自己）。点击目标成员后弹出确认框，确认后调用memberApi.transfer接口完成转让。

页面底部的操作栏根据用户角色动态显示不同的按钮组合：非成员显示"加入社团"按钮；社长显示"编辑"、"发布活动"和"转让社长"三个按钮；副社长显示"发布活动"和"退出社团"两个按钮；普通成员仅显示"退出社团"按钮。这种基于角色的动态UI通过计算属性（computed）实现，根据当前登录用户在社团成员列表中的角色信息进行判断。

#### 5.3.3 活动详情页

活动详情页是系统中功能最丰富的页面，集成了活动信息展示、报名、签到、评价等多个交互功能。

页面结构自上而下包括：封面图区域（有封面图时显示，支持点击预览大图）、标题与状态标签区（绿色渐变背景）、基本信息区（地点、开始时间、结束时间、参与人数、所属社团）、活动详情区（描述文本、标签列表、图片画廊）、已报名人员列表区和活动评价区（显示平均评分和评价列表）。

在签到功能方面，当用户点击"签到打卡"按钮时，系统首先检查活动是否已开启签到码（通过activity.checkinCodeEnabled字段判断）。若未开启签到码，直接调用签到接口完成签到；若已开启签到码，弹出签到码输入弹窗，用户输入6位数字签到码后调用签到接口，后端验证签到码正确性后完成签到。签到码输入框设置为数字类型、最大长度6位，使用大号字体和蓝色配色，便于用户输入。

在评价功能方面，已签到的用户可以点击"评价活动"按钮打开评价弹窗。弹窗包含5星评分选择器（点击星标设定评分，已选星标为金色）和文字评价输入框。提交评价后调用feedbackApi.submit接口，后端通过唯一索引防止重复评价。

在图片管理方面，活动组织者可以在活动详情页直接管理活动图片。图片画廊以3列网格形式展示，每张图片右上角显示删除按钮（仅组织者可见），点击删除按钮后二次确认再执行删除操作。上传按钮使用虚线边框样式，调用uni.chooseImage选择图片后通过uni.uploadFile逐个上传到服务器。

#### 5.3.4 签到码功能

签到码功能是本系统的特色模块，通过前端的签到记录管理页面（manage/checkins）和后端的签到码相关API协同实现。

签到记录管理页面分为两个区域：签到码管理区和签到记录列表区。签到码管理区根据签到码的启用状态显示不同的界面——未启用时显示说明文字和"开启签到码"蓝色按钮，并提示"开启后参与者必须输入签到码才能签到，确保到场验证"；已启用时以超大号蓝色字体（80rpx）和蓝色背景（#E3F2FD）展示当前6位签到码，下方提供"刷新签到码"和"结束签到"两个操作按钮。

签到码的生成通过后端的POST /api/activities/:id/checkin-code接口实现，接口生成一个随机的6位数字码并保存到活动文档的checkinCode字段，同时将checkinCodeEnabled设为true。刷新签到码调用同一接口，生成新的6位码后旧码立即失效。

"结束签到"操作通过POST /api/activities/:id/checkin-code/stop接口实现，接口将活动状态更新为ended，并将endTime更新为当前时间，确保后续签到请求因时间校验不通过而被拒绝。结束签到前通过uni.showModal弹出确认框，明确告知"结束后活动将标记为已结束，未签到的人将无法再签到"。

签到码一旦启用不可关闭回无码模式的设计是本系统的重要业务规则。这一规则的目的是防止组织者在签到进行中关闭签到码后允许未到场者补签，确保签到数据的真实性。

签到记录列表区以蓝色渐变背景的统计栏显示总签到人数，下方以卡片列表展示每位签到者的姓名首字母头像、昵称、学号和签到时间。

#### 5.3.5 消息中心

消息中心页面实现了站内通知的完整展示和交互功能。页面顶部在有未读消息时显示未读数量和"全部已读"操作按钮。通知列表以卡片形式展示，每个通知卡片包含类型图标（不同类型使用不同的emoji和背景色）、标题、内容和时间。未读通知使用浅蓝色背景（#F3F8FF）并在右侧显示红色圆点标记，已读通知使用白色背景。

在通知类型图标方面，系统为不同的通知类型设计了直观的图标标识：审核相关使用📋图标、通过使用✅图标、拒绝使用❌图标、撤回使用↩️图标、加入使用👤图标、离开使用👋图标、提醒使用⏰图标。

在时间显示方面，消息中心使用了智能的相对时间格式化函数：1分钟内显示"刚刚"、1小时内显示"X分钟前"、24小时内显示"X小时前"、7天内显示"X天前"、超过7天显示"X月X日"。

在点击交互方面，点击通知时首先调用markRead接口标记为已读，然后根据通知类型进行智能跳转：club_pending类型跳转到社团审核页面、club_rejected类型跳转到我的社团页面、club_withdrawn类型仅显示Toast提示"该申请已撤回"、club_approved和成员变动类型跳转到社团详情页、registration相关类型跳转到活动详情页。跳转前会验证关联资源是否存在（如社团是否已被删除），不存在时显示友好的错误提示而非跳转到空页面。

#### 5.3.6 社团审核

社团审核页面是系统管理员专用的管理界面，用于处理社团创建申请。页面通过调用clubApi.getPending接口获取所有状态为pending的社团列表。

每个待审核社团以卡片形式展示，包含社团名称首字母的橙色圆形头像、社团名称、分类、简介和申请人昵称。卡片底部提供"通过"（绿色按钮）和"拒绝"（灰色背景红色文字按钮）两个操作按钮。

点击"通过"按钮直接调用clubApi.approve接口完成审核通过操作。后端在审核通过时自动执行以下步骤：将社团状态更新为active、将申请人的系统角色从student升级为club_admin、向申请人发送审核通过的通知消息。

点击"拒绝"按钮时弹出模态框，包含文本输入区域供管理员填写拒绝原因（必填）。填写完成后点击"确认拒绝"按钮调用clubApi.reject接口。后端在审核拒绝时将社团状态更新为inactive、将拒绝原因保存到rejectReason字段、向申请人发送包含拒绝原因的通知消息。拒绝原因的必填校验在前后端均有实现——前端检查输入是否为空并提示"请填写拒绝原因"，后端同样验证reason参数的有效性。

审核操作完成后页面自动刷新待审核列表。当所有待审核社团处理完毕后，页面显示"暂无待审核的社团"的空状态提示。

### 6.3 易用性测试

易用性测试通过邀请若干名测试用户进行实际操作体验来评估系统的用户友好程度。测试用户包括不同角色（普通学生、社团管理者、系统管理员），要求他们在不看任何使用说明的情况下独立完成指定的操作任务，并记录操作过程中遇到的问题和主观感受。

测试结果表明：

（1）页面导航方面。所有测试用户均能在30秒内通过TabBar导航找到目标功能入口，页面层次清晰、导航直观。

## 第七章 总结与展望

### 7.1 总结

本文围绕校园社团活动管理的实际需求，设计并实现了一套基于Uniapp的校园社团活动管理小程序系统。论文的主要工作和成果总结如下：

（1）完成了系统的全面需求分析。通过对校园社团管理场景的深入调研，梳理了三种系统级角色（学生、社团管理员、系统管理员）和三种社团内角色（社长、副社长、普通成员）的权限体系，明确了十大核心功能模块和六种活动状态的完整业务模型，为系统设计和开发奠定了坚实基础。

（2）完成了系统的架构设计和数据库设计。采用前后端分离的三层架构（表现层、业务逻辑层、数据持久层），设计了7个MongoDB数据模型，合理运用了嵌套文档、数组字段和唯一索引等MongoDB特性，实现了高效的数据存储和查询。

（3）完成了系统的全栈开发。前端使用Uniapp框架（Vue 2模式）开发了20个页面，后端使用Node.js + Express框架构建了43个RESTful API接口，实现了社团管理、活动管理、签到打卡、消息通知等全部核心功能，总代码量约4764行。

（4）设计并实现了签到码验证机制。创新性地实现了"组织者发码→参与者验码"的签到流程，通过6位随机数字码验证参与者到场。签到码一旦启用不可关闭（只能刷新或结束签到），有效防止未到场者事后补签，保证了签到数据的真实性。

（5）实现了完整的社团审核流程。社团创建申请需经管理员审核（通过/拒绝并填写原因），被拒绝的社团支持查看拒绝原因后修改重新提交或撤回申请，形成了完整的审核业务闭环。

（6）建立了站内消息通知系统。覆盖11种业务触发场景（社团审核、报名审核、成员变动等）的自动通知机制，确保各角色能够及时获取关键业务信息。

（7）通过了全面的系统测试。57个自动化API测试用例全部通过（通过率100%），开发过程中共发现并修复34个Bug，系统功能完整、运行稳定。

### 7.2 展望

尽管本系统已经实现了校园社团活动管理的核心功能，但仍存在以下不足之处，可在后续版本中进一步改进和完善：

（1）微信生态深度集成。当前系统使用用户名密码的传统登录方式，未集成微信授权登录功能（需要已通过认证的小程序AppID）。后续可以接入微信登录、微信支付（活动收费场景）、微信模板消息推送等微信生态能力，进一步提升用户体验。

（2）数据统计与分析。当前系统缺少数据可视化和统计分析功能。后续可以增加社团活跃度排名、活动参与率统计、签到率分析、评价趋势图表等数据看板功能，为社团运营决策提供数据支持。

（3）实时通信能力。当前的消息通知采用客户端轮询（拉取）模式，存在一定的消息延迟。后续可以引入WebSocket技术实现服务端主动推送，提升消息的实时性和用户体验。

（4）图片存储优化。当前系统使用服务器本地磁盘存储上传的图片文件，在多服务器部署和大流量场景下存在局限性。后续可以改用云存储服务（如阿里云OSS、腾讯云COS等），提升图片存储的可靠性和访问速度。

（5）搜索功能优化。当前的社团和活动搜索基于MongoDB的正则匹配实现，在大数据量场景下性能有限。后续可以引入Elasticsearch等全文搜索引擎，支持更丰富的搜索维度和更高效的检索性能。

（6）权限体系细化。当前的权限控制粒度有限，后续可以引入更细化的RBAC（基于角色的访问控制）模型，支持自定义权限组和更灵活的权限配置。
